# Portfolio description

For use on Upwork, LinkedIn, or a portfolio site. Live demo: **https://ai-support-desk-gilt.vercel.app** · Source: **https://github.com/MMSolver/ai-support-desk**

---

**AI Support Desk** is a full-stack customer support ticketing app I built end to end — a support agent's dashboard where every incoming ticket is automatically triaged by an LLM. A customer describes their issue in a form; the backend calls OpenAI's `gpt-4o-mini` with a JSON-Schema-constrained prompt and gets back a category, a priority level, a short summary, and a drafted reply, all persisted to Postgres and surfaced live on a stats dashboard with filtering and pagination. It's built as a production-shaped MVP, not a demo: real database, real AI calls, real deployment, real test suite — no hardcoded or scripted "AI" responses anywhere in the flow.

Technically, it's a Next.js 16 App Router project (Server Components + API Route Handlers in one deployable unit) backed by Supabase Postgres, styled with Tailwind CSS 4 and shadcn/ui, and fully typed end to end with TypeScript in strict mode and Zod validating both the client form and the server boundary. The part I'd point to first is the AI reliability design: the ticket is written to the database _before_ the AI call ever runs, so a failed OpenAI request — a timeout, a rate limit, an API key issue, a malformed response — never loses the customer's message; it's flagged `needs_review` instead and the UI degrades gracefully with a clear banner and toast. I write the Zod schema once and share it between the client (for instant form feedback) and the server (the actual source of truth), and I double-validate every LLM response against it even though OpenAI's own `strict: true` JSON Schema mode already constrains the shape — belt and suspenders on a boundary I don't fully control.

Quality and shipping practices: 88 Vitest unit/integration tests and 5 Playwright end-to-end tests (run against a real production build, hitting the real DB and AI API) all passing; strict TypeScript with zero `any`-shaped escape hatches; a locked-down Content-Security-Policy and the standard security headers on every response, verified to differ correctly between development and production; secrets confirmed absent from the client bundle before every deploy; and a deployment pipeline on Vercel with zero extra configuration beyond environment variables. Every architectural decision — why Supabase over raw Postgres, why `gpt-4o-mini` over a larger model, why a single `tickets` table instead of a normalized schema — is written down with its rationale in the repo's `PROJECT.md`, the way I'd document a real production system for the next engineer who touches it.
